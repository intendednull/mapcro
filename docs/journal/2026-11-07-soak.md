# 2026-11-07: a many-peer soak on the real stack

The simulation (`crates/sim`) runs 9 peers through chaos, but in-process and engine only. The
real-stack tests stop at 2 or 3 peers. This entry is about the soak that fills the gap: 40 people
on one board through the real server, and what it found.

## What it is

`just soak [seed] [peers] [seconds]` (spec §14, layer 2a). It starts the real server binary. It
then runs 40 real `BoardSession`s (30 editors, 10 viewers) over the real WASM replica, each with
its own IndexedDB (`fake-indexeddb`), in worker threads. A seeded schedule drives a few actions per
second per editor, with bursts:
- hero drags (a presence preview, then one transaction) and group moves,
- souls, clocks and ults,
- ink, arrows, callouts, notes, objectives and waves,
- scene add, reorder and delete,
- undo and redo,
- cursors, lasers and follows,
- every couple of seconds, several editors writing one field within milliseconds of each other.

The faults:
- socket drops,
- tab reloads,
- offline bursts that keep editing,
- a late joiner from scratch on a large log,
- the server `kill -9`'d and restarted mid-run.

A reload kills the tab as a crash would. Saves not yet started never happen, and saves in flight
are lost; the next tab loads only what had landed.

At the end everyone reconnects and drains. Then it checks what the simulation checks:
- every replica equals the log replayed from the server and a fresh client's board;
- every transaction a peer saw acked is logged exactly once, at that seq, with the same contents;
- every rejected one is not logged, and its peer heard the rejection;
- presence has converged;
- the final board passes `validate_doc`.

During the run, protocol errors and `Fatal`s fail it at once. On a peer's first failure it prints
the last 60 things that peer did and saw (saves, loads, hellos, sends, acks, rejections, reloads).
That trace is what found the first bug.

The same seed gives the same schedule; the run prints its fingerprint. Network timing still
varies.

## What it found

I expected it to pass. The simulation covers the protocol and the model covers the design, so I
thought the real stack would only add plumbing. Instead it found three real bugs, all in the
TypeScript session, which nothing below it exercises:

1. **Pending work resent before it was durable** (fixed in 9780996). On reconnect, the session
   sent the hello and every pending transaction at once, outside the save chain.
   - An edit made while the socket was down could be acked before its IndexedDB write landed.
   - If the tab then died, the reopened tab reused the cseq. Its catch-up delivered its own entry
     with nothing pending to match it: AckMismatch, reconnect, the same again, forever.
   - Worse, an edit made before Ready was silently swapped for the old one.
   - It showed up in the first 10-minute run as peers that never quiesced. The trace showed a
     hello resending `#263..#267` while the saved state stopped at `next_cseq 265`.
   - Regression test: `web/test/resend-durable.test.ts`.
2. **A restored view session accepted an edit before Ready** (fixed in 0d7047f). `readOnly` was
   learned only from Ready.
   - The edit was persisted, then resent on every connect, each resend a `Fatal`.
   - Ready reset the backoff, so it looped at the minimum delay.
   - The UI never called `edit()` that early, so users couldn't hit it; the session's contract
     allowed it.
3. **A long offline stretch reconnected as a storm of abuse closes** (fixed in 0d7047f). The
   resend went out in one burst, past the server's 300 frames. The server closed the socket as
   `abuse`, the session reconnected and resent everything left.
   - It did drain: 400 edits in 4 s through 47 closes, 2000 in 78 s through 683.
   - Now 2000 drain in 60 s with no closes.
   - Regression test for 2 and 3: `web/test/soak-regressions.test.ts`.

Not fixed, for the record:
- **An auth timeout looks like a bad link.** The server answers a socket that doesn't
  authenticate within 10 s with `unauthorized`, which the session treats as final. A tab frozen
  between opening its socket and sending auth stays shut out until it reloads. Three peers hit
  this when an overloaded run's workers stalled.
- **Acks wait on fsync.** One room writes each transaction with `synchronous=FULL` before it
  acks. At 57 transactions a second, the median ack was 148 ms on this disk and 7 ms on tmpfs,
  for the same schedule.
- **Catch-up costs a full document diff per entry on the client.** The late joiner took 59 s for
  23,000 entries in the long run, on a busy worker.

## Numbers

- **Default, on HEAD after the fixes (fb4ab1a):** 40 peers for 60 s, 3 crashes, 76 drops, 45 reloads, 41
  offline bursts. 3461 transactions, 60 real conflicts, 55 rejections. Ack p50 35 ms, p99 520 ms.
  Peak server RSS 30 MB. Quiesced in 1.3 s; a fresh client loaded everything in 0.8 s.
- **Ten minutes on fb4ab1a:** 32,809 transactions, 8 crashes, 840 drops, 478 reloads, 309 offline
  bursts. Ack p50 40 ms, p99 2.7 s. Peak RSS 55 MB. No failures. The late joiner arrived at seq
  23,421 and caught up in 47 s on a busy worker; a fresh client on an idle thread loaded all 32,809
  entries in 23 s (about 0.7 ms each).
- **Ten minutes on 6a2db1d** (after the first fix): 33,481 transactions, 8 crashes, 847 drops,
  479 reloads. Ack p50 25 ms, p99 2.1 s. Peak RSS 62 MB. Quiesced in 1.3 s. Every end-of-run
  check held. The one live failure was the harness's own: a reloaded tab's hello superseded the old
  tab's connection, and that Fatal landed on a socket already let go. It's now ignored there.
  The same seed had failed before the fix. That run is also how I learned an overloaded machine
  matters: load 65 on 16 cores, scheduling lag 58 s, p50 4.7 s.
- **At the session cap:** 64 peers, default history caps. A 65th gets a clean `closed: full`, and
  nobody else notices.

## Does it discriminate

Bugs planted one at a time, each in a worktree, then restored:

| Planted bug | Caught | How fast |
|---|---|---|
| The server drops one outgoing message in 1000 | yes | 2.5 s: a gap becomes a protocol error |
| The server applies a resent transaction again (no dedup) | yes | 3.7 s: acked twice, then AckMismatch |
| Presence batched, each batch's last update dropped | yes | at the end: stale and missing presence |
| The hello claims nothing is pending (skips `pending_from`) | at 4× faults | 10.5 s; missed in a default 60 s run |
| The client sends an edit before persisting it | at 4× faults, with crash-like reloads | 25 s: a cseq reused, then AckMismatch; missed in a default 60 s run |
| The server acks and broadcasts before the write is durable | **no** | missed with 3, 12 and 40 crashes (180 s) |

Three lessons:
- The harness's first model of a reload was too kind. In-flight saves always finished, so
  "send, then save" passed. A real crash loses uncommitted IndexedDB transactions, and modelling
  that is what a persistence bug needs.
- Some bugs need rarer interleavings than a minute gives: a rejection lost in exactly the
  disconnect. Raising the fault rate finds them in seconds; a default run doesn't. Both are flags:
  `--faults 4`, `--seconds 600`.
- Killing the server at random times doesn't test "durable before ack". The window between an ack
  leaving and its fsync is well under a millisecond, and 40 random kills never landed in it. That
  needs a kill at a chosen point (a failpoint after the broadcast), which belongs in the Rust
  system tests (layer 2), not here.
- Ack-first, done crudely (writes in the background, out of order), was caught in under a second,
  but by the side effect: catch-up found holes and closed every socket with `storage_failure`.

A false positive along the way: a new optional presence field (`picked`) came back from the
server as `picked: []`. Exact JSON comparison called that stale. Presence is now compared with
keys sorted, and an absent field counts the same as null or empty.
