# 2026-11-08: Changing values ease, everywhere

Health began easing in 6c0b59e (easeOutExpo, 350 ms). The operator then said: "UI elements that
represent changing values should follow suit", and later "timers for example". This pass turns
that into one convention (spec §4a) and applies it to every changing value Player shows.

## The convention

- **CSS.** `--value-ease-ms` (350 ms) and `--ease-out-expo` sit on `:root` in `styles/app.css`.
  One reduced-motion rule sets the duration to 0. A transition with no duration creates no
  animation, so every eased property jumps. `--hp-ease` was retired, and its three uses moved
  over; the per-element reduced-motion rules went with it.
- **JS.** `easedNumber(source, ms)` lives in `board/smooth.ts` beside `smoothed`. Its pure core is
  `NumberEase`. `smoothed` was a poor fit to extend: it is linear, works on positions only, and
  runs at 100 ms for presence.
  - The first value, a value after `null`, a hidden tab and reduced motion all snap.
  - The same target read again keeps the ease that is running. Player's top bar re-reads its
    sources every frame while playing; without this the ease would restart each frame and never
    finish.

## Each element

| Element | Eased? | How, and why |
|---|---|---|
| Player top bar ult ring | Yes | A typed `@property --left` with `initial-value: 100%`, so a ring entering cooldown doesn't sweep in from empty. The ult steps each second. |
| Scene top bar ult ring | No | Set by hand, by dragging or scrolling; easing it would lag the pointer and its handle. |
| Souls, Player top bar | Yes | `easedNumber`; they count up through a sample's step. `data-souls` stays exact. |
| Team soul totals | Yes | `easedNumber`, the same way. |
| Scene bar souls | No | Typed by hand. |
| Respawn countdown (top bar) | Yes | `easedNumber` on the continuous seconds left, shown as `Math.ceil`. A long scrub runs down through the seconds. During playback it trails by about 45 ms of wall time. At 8× that is under 1 s of game time, so the number can read 1 high for a moment. |
| Zipline colour edges | Yes | `easedNumber` per lane edge in Board.tsx (MapView is buffs-timers'). They stepped every second. The edges are in the map's 0..1000 units, so a zoom doesn't move them and isn't eased. |
| Upload bar and percent | Yes | `easedNumber` on the bytes sent; `data-loaded` keeps the exact value. |
| Queue position / ETA text | No | Ordinal and labels, not a quantity being drawn. |
| Trooper dots, hero tokens | Already | Interpolated between samples by playback time (`troopersAt`, `positionAt`), plus the 350 ms scene-flip glide. Nothing to add. |
| Scrubber thumb, match clock | No | They are the playback position; easing them would put them out of step with the pointer and the map. |
| Camp, urn and objective timers in tooltips | No | Hover text can't animate meaningfully, and buffs-timers owns those tooltips. |
| `match/preview.tsx` `UltRing` | No | Not rendered anywhere (Player.tsx imports it unused). |

## Tests

- **`e2e/player-ease.spec.ts`.** It scrubs 25 s to 75 s and samples each frame in the page for
  500 ms.
  - Normal motion: the countdown, souls, total and zipline edge each pass through more than two
    in-between values, move one way only, are past 60% of the way at every frame from 100 to
    200 ms (expo reaches 86% at 100 ms; linear would be at 29%), and land on the exact value.
  - The ult ring's running transition is `--left cubic-bezier(0.16, 1, 0.3, 1) 350`.
  - Reduced motion: the first frame already shows the end value, and the ring has no transition.
  - Upload: a 1 MB/s throttled upload shows frames where the bar trails the last progress event.
    With reduced motion, no frame trails.
- **Mutants**, each killed:
  - removing the ult CSS transition, and each of the five `easedNumber` uses;
  - removing the reduced-motion CSS rule, which also fails `player-health.spec.ts`;
  - removing the reduced-motion check in JS;
  - swapping the expo curve for a linear one. This mutant first survived, and the 100–200 ms
    check was added for it.
- **Unrelated failures.** `player-tier.spec.ts:67` and `upload-ux.spec.ts:208` (upload offered,
  or the drop overlay shown, with the full replay) also fail with the base commit's client,
  against the server binary that was current at the time. They are not caused by this pass.
