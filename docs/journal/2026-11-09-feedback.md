# 2026-11-09: A feedback button that opens GitHub issues

The operator asked: "Can we add a feedback button? that just all it does is asks for a title and
a description and then when the user submits, it just creates an issue in the Github repo." The
design is in the architecture spec §11a; enabling it is in docs/deploy.md.

## What changed

- **Server.** `crates/server/src/feedback.rs`: `GET /api/feedback` → `{enabled}`, and
  `POST /api/feedback` → a GitHub issue, labelled `feedback` (retried once without the label on
  a 422), with a build footer. Cleaning, lengths and `@` neutralising happen on the server. The
  limits are 3 an hour per client key and 30 a day overall, as sliding windows. The token comes
  from `FEEDBACK_GITHUB_TOKEN_FILE`, wired like the deadlock-api key: module option
  `feedbackGithubTokenFile`, `LoadCredential`, `%d/feedback-github-token`. There are also
  `feedbackGithubRepo`, `feedbackPerClientPerHour` and `feedbackGlobalPerDay`.
- **Metrics.** `feedback_sent` and `feedback_rejected{reason}`; GitHub failures also go in the
  failures log, and `stats summary` shows both under USAGE.
- **Client.** `web/src/ui/Feedback.tsx` (the button and the dialog) and `web/src/ui/modal.ts`
  (the keyboard contract: Portal, `inert` background, Tab wrap, focus return).
- **VM check.** With the option unset, the unit starts, `/api/feedback` says
  `{"enabled":false}`, and there's no token variable.

## Choices, and why

- **A bad token file turns the form off; it doesn't stop the server.** That's what the
  deadlock-api key does, and a feedback form shouldn't be able to take the site down. A
  malformed repo or API base is a config error and stops the server at start, like other
  config.
- **The joiner goes after every `@`, on the cleaned text, after the length check**, so the
  sender's 120 characters stay 120 and nothing they type can undo it. A title of 120 `@`s is
  valid.
- **The body cap is 32 KiB, not the API's 16 KiB.** 5,000 characters of emoji are 20 KB of
  UTF-8. Like the replay upload route, the route sits outside the global layer with its own cap.
- **A GitHub failure still spends the client's slot.** Otherwise a failing GitHub could be
  called without limit. The client keeps the text, so trying again costs nothing to type.
- **Off is 404, not 503,** so a disabled form isn't counted as a server failure.
- **Title and description lengths use the browser's `maxLength`** (UTF-16 units). That's never
  more than the server's character count, so the client can't send a length the server refuses.
- **The success link must be `https://`**, checked on the server and the client, because the
  browser renders it as a link.

## Tests

- Rust unit tests: cleaning, control characters and CRLF; neutralising (`@user`, `@org/team`,
  `a@b`, `@@`); validation of the cleaned length in characters; the limiter's windows and
  Retry-After.
- Rust integration tests (`crates/server/tests/feedback.rs`, against a fake GitHub on
  loopback): the exact request (path, bearer, API version, accept, User-Agent, title, body with
  footer, label); no sender address, agent or forwarding header reaches GitHub; nothing of the
  text, the token or the sender in the log or the database. Also the label retry (and only
  one), 5xx, an unreachable GitHub and a non-https link becoming a clean 502, invalid input
  never reaching GitHub, per-client (/64) and global 429s with Retry-After, off in three ways,
  bad config, and the stats and failures rows.
- e2e (`web/e2e/feedback.spec.ts`): open from the board and from the landing; validation
  messages; the count near the limit; send → "Thanks — sent" with the issue's link; a 429's
  wording with the text kept; hidden when off; Escape, Tab and Shift+Tab wrap, the background
  inert, focus returning to the opener, and Space on a dialog button not swallowed by the
  board.
- Mutations, each reverted after: neutralising off, no label retry, no per-client limit, no
  global limit, control characters kept, no Retry-After header (server); no Tab wrap, no
  `inert`, no stopPropagation, no focus return, no Retry-After wording (client). Every one
  failed a test. Without stopPropagation the failure was a surprise: Escape closed the dialog
  and returned focus, and then the board's window Escape handler (`leaveControl`) blurred the
  opener.

## Surprises

- **The read hook counts newline bytes in PNGs**, so most screenshots couldn't be read
  directly. Re-encoding them as JPEGs in /tmp got around it.
- **None of the existing dialogs contain focus.** Share, Clone and the hero picker all let Tab
  out. That's logged in the backlog; `modal.ts` is the fix ready to adopt.

## Follow-up: cross-repo references (lead, same day)

The issues are opened under the operator's account, so `owner/repo#123`, `owner/repo@sha` and
GitHub issue, PR, commit or discussion URLs would have put "intendednull mentioned this"
backlinks into strangers' repositories. That's abuse under the operator's identity, so it's
fixed rather than left in the backlog. `neutralise` now adds a joiner after a `#` that follows a
name character and inside every `github.com`; `@` was already covered. A plain `#123` stays a
link. A unit test and the fake-GitHub test check that nothing linkable is left. Mutations (no
`#` rule, no `github.com` rule, `#` everywhere) each failed a test.
